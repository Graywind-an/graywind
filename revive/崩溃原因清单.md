## 速查：体检报告指到哪一条

| 体检输出 | 大概率是哪一条 |
|---|---|
| 03 崩溃日志「异常」，弹窗写 `Web authentication failed` | **第 1 条** cookie 撑爆 |
| 03 + crash 里出现 `does not provide an export named` | **第 2 条** 插件 export 不存在 |
| 03 + crash 里错误指向某个 bundle 的解析 / 加载 | **第 3 条** 第三方 bundle 解析错误 |
| 界面卡在 profile 选择，只剩「打开恢复模式」 | **第 4 条** 升级不兼容 |
| 双击没反应 / 秒退，事件日志 `0x80000003` | **第 5 条** GPU 子进程崩溃 |
| 01 程序本体「致命」 | 程序文件没了 —— 先按 01 修（多半是第 3/4 条的后果） |
| 02 profile 配置「致命 / 异常」 | 配置丢了或坏了 —— 先按 02 修（多半是第 2/3 条的后果） |

**一句总规矩**：先看 03 的最新一份 crash 日志再动手。**同一个症状别重新猜** —— 报错出现就去翻这份清单和 crash 日志。

## 1. cookie 累积撑爆请求头（最常见、已验证）

**症状**

- 双击图标，闪一下就崩，弹窗：
  ```
  The application could not start or stopped unexpectedly.
  desktop welcome: Web authentication failed
  ```
- **重装、覆盖安装都没用**（`%APPDATA%` 不跟着重装走）
- 之前一直好好的，是「最近某天开始」的；越常开越接近崩

**怎么判断**（任一条成立就基本确诊）

1. 看 cookie 库大小：
   ```powershell
   (Get-Item "$env:APPDATA\@deepseek-ai\dsh-desktop\Network\Cookies").Length
   ```
   - **20,480 B 左右** = 空库，干净
   - **5 万字节以上** = 堆了四五十条，该清了
   - 本机实测：崩之前 53 KB，清完 20 KB
2. crash 日志里有 `431` 或 `Web authentication failed` 字样（体检 03 会报最新一份的时间）
3. 体检结尾的「附注」会直接打出 Cookies 当前字节数

**为什么**

DSH Desktop 每次启动用**随机端口**，认证 cookie 的名字由 `host:port` 推导 —— **每启动一次就多一条** `dsh-auth-*`，30 天有效期，没有任何地方回收。约 70 条时一起塞进请求头，超过 Node 默认的 **16 KiB** 上限 → 服务器返回 **431**（HTTP：请求头过大）→ 启动时崩。

**这个死法最难查**：报错像网络/认证问题，弹窗里「禁用第三方插件并重启」是空的，重装也无效。

**怎么修**

1. 托盘里**完全退出** DSH（不是关窗口）
2. 删 `%APPDATA%\@deepseek-ai\dsh-desktop\Network\Cookies`，连带 `Cookies-journal` / `-wal` / `-shm`
3. 再启动。**数据不丢** —— 重启会自动重新认证，会话、聊天记录、配置都在
4. 长期：每次启动前跑 `Clear-Cookies-Start-DSH.cmd`（复活菜单按 **1**）

**判据（可指着看）**：修完 Cookie 库回到 2 万字节左右；每次启动后再看，**只 +一条**。如果一次加很多，说明有别的东西也在写这个库。

**来源**

- 我们自己机器上的原始记录：`复活包\README-清cookie必读.md`（2026-11-01 实测；含手动修法）
- 同一个修法在本复活包里做成了 `清cookie并启动.cmd`（复活菜单按 **1** 就它）
- 原始出处按那份 README 记的是 GitHub `deepseek-ai/deepseek-harness` 讨论 **#11408**

## 2. 插件 import 了不存在的 export

**症状**

- 启动就崩，崩在**加载插件**那一步（不是界面渲染）
- 错误里能读到这些字眼之一：
  - `does not provide an export named 'xxx'`
  - `SyntaxError: The requested module ... does not provide an export named`
  - `Cannot find module`（同类，指向某个插件入口）
- **时间点很关键**：通常是「刚装了 / 刚升级了某个插件之后」开始崩

**怎么判断**

1. 打开最新一份 crash 日志（`%APPDATA%\@deepseek-ai\dsh-desktop\logs\crash-*.log`），搜 `does not provide an export` / `Cannot find module`
2. 看配置最近改过谁：
   ```powershell
   Get-ChildItem "$env:USERPROFILE\.dsh\profiles\desktop\package.json","$env:USERPROFILE\.dsh\profiles\desktop\cordis.patch.yml" | Select-Object Name,LastWriteTime
   ```
   再对一眼 `profiles\desktop` 里的 `.bak-*` —— **改配置的时间点和开始崩的时间点对得上，就是它**
3. 还判断不出就二分：把最近加的那个 bundle 从 bundles 里摘掉再启动；能起来 = 就是它

**怎么修**

1. 摘掉那个 bundle（先备份 `package.json` 和 `cordis.patch.yml`）
2. 或者用同目录的 `.bak-*` 回退到崩之前那一份（`package.json.bak-*` / `cordis.patch.yml.bak-*`）
3. **不要去改插件源码**（除非是你自己写的那个插件）—— 改源码是把别人的 bug 搬进你的目录

> 体检只能告诉你「崩过、什么时候崩的」，**不能替你指认是哪个插件** —— 这一步必须看 crash 日志里的包名。

**来源**：GitHub `deepseek-ai/deepseek-harness` issue **#5864**

## 3. 第三方 bundle 解析错误 —— 一个坏 bundle 拖垮整个桌面壳

**症状**

- 整个界面起不来（白屏 / 直接崩），**不是某个插件功能坏了，是整个壳挂了**
- 错误发生在 bundle 的**解析/加载**阶段：报错里带 bundle 名 + 语法/解析类信息（不是某个插件自己抛的业务错误）
- 常见于装了某个版本不匹配的第三方 bundle、或 bundle 的 `main`/`exports` 字段写错

**怎么判断**

1. crash 日志里的报错**指向某一个 bundle 的解析**，而不是某个 API 调用
2. 其余 bundle 单独看都正常 —— 把可疑那个从 `dsh.profile.bundles` 去掉后**能起来**
3. 和「第 2 条」的区别：第 2 条是 **export 名字对不上**（依赖/版本问题）；这条是 **bundle 本身解析不了**（文件/格式问题）

**怎么修**

1. 备份 `package.json`，把那个 bundle 从 `dsh.profile.bundles` 里移出
2. 要保留这个功能就换回能用的旧版本；换版本前先备份
3. 配置坏了、又没有备份 → 用体检 **02** 从镜像补回 `package.json` / `cordis.patch.yml`

**来源**：GitHub `deepseek-ai/deepseek-harness` issue **#11440**

## 4. 升级不兼容 —— 卡在 profile 选择，只剩「打开恢复模式」

**症状**

- 程序能起，但界面停在 **profile 选择**，点不动，只剩一个「打开恢复模式」
- 时间点：**刚升级完**（程序版本比 profile 配置新）
- 主界面进不去，所以「在 DSH 里修 DSH」这条路被堵住

**怎么判断**

1. 看程序目录的时间戳是不是今天/刚换过：
   ```powershell
   Get-Item "$env:LOCALAPPDATA\Programs\DeepSeek Harness\resources\app.asar" | Select-Object LastWriteTime
   ```
   再对一眼 `~\.dsh\profiles\desktop\package.json` 的 LastWriteTime —— **程序比配置新很多**，就是这条
2. 看 `profiles\desktop` 里有没有升级前留下的 `.bak-*`（有就说明最近动过配置）
3. 体检 02 会报 bundles 数量：**0 个**或 JSON 解析不了，也指向这条

**怎么修**（从最安全的开始）

1. **恢复模式**里先选一个能进的 profile —— 进去了再慢慢修配置
2. 换回旧程序：用镜像的 `app\` 覆盖主机程序目录（**先备份主机的程序目录**，只换程序、不碰数据），这就是菜单按 **2** 的思路
3. 配置被升级改写、缺件 → 体检 **02**（从镜像的 `dsh-home\profiles` 补回 `package.json` / `cordis.patch.yml`）；已有文件内容不同的话要显式加 `-Overwrite`，脚本会先备份
4. 都不行：**别自己重装、别删 `~\.dsh`** —— 停手，把体检报告给 AI

**来源**：GitHub `deepseek-ai/deepseek-harness` issue **#724**

## 5. GPU 子进程崩溃 —— 双击没反应，`0x80000003`

**症状**

- 双击图标**没反应**，或者窗口闪一下就没了
- 进程可能起过又死（体检 00 会显示 0 个进程，或进程数在变）
- 系统事件日志里退出码 `0x80000003`（= Windows 的 `STATUS_BREAKPOINT`，断言/断点型异常）
- 常和显卡驱动 / 渲染进程一起出现（`renderer` 类 crash 日志）

**怎么判断**

1. 看事件日志里的最近一条应用程序错误：
   ```powershell
   Get-WinEvent -FilterHashtable @{LogName='Application'; ProviderName='Application Error'} -MaxEvents 5 |
     Select-Object TimeCreated, Message
   ```
   消息里 **`0x80000003`** 或故障模块涉及 `d3d*` / 显卡驱动 dll = 这条
2. 直接试：启动参数加 `--disable-gpu`（关掉 GPU 加速）能起 = 基本确诊
3. crash 日志名带 `renderer` 的，优先怀疑这条（体检 03 会报最新一份的文件名）

**怎么修**

1. 先用 `--disable-gpu` 起一次，确认能进（能进就说明是 GPU 侧）
2. 更新显卡驱动；装完还是崩 → 用下面这条长期关掉 GPU：
   ```
   "<程序目录>\DeepSeek Harness.exe" --disable-gpu
   ```
   并把这个参数写进你的快捷方式（不要让每次都要手打）
3. 关掉 GPU 后界面可能更慢，但**能用优先**
4. 别为了这条重装 DSH —— 重装不解决驱动问题

**来源**：GitHub `deepseek-ai/deepseek-harness` discussion **#332**

## 不在上面五条里怎么办

按这个顺序，**别跳**：

1. **体检 03 的最新一份 crash 日志开头**（体检会直接打出来）—— 报错原文是最硬的线索
2. 翻 `memory\踩坑账本.md` 和 `~\.dsh\notes\备忘录-*.md`：**同一个症状 三天内可能已经踩过一次**
3. 对上「时间点」：最近改了什么（装插件 / 升级 / 改配置 / 换驱动）—— 改的时间点和开始崩的时间点对得上，先回退那个
4. 三条都不成立 → **停手，把体检报告 + crash 日志交给 AI**。不许自己重装、不许删 `~\.dsh`、不许格式化
